# 給冷讀者寫字

## 0. 適用範圍：只要是給人看的字，全部

不分載體。程式碼註解、commit message、PR/MR 留言、review finding、設計文件、教學筆記、給非作者看的說明、session 回話——全部同一套標準。

**唯一判準**：把這段字丟給讀者，他**只憑手上真的有的東西**讀得懂嗎？讀不懂＝重寫，不是補一句「詳見 xxx」。

---

## 1. 先確定這次的讀者少了什麼

不對稱有兩種來源，決定哪幾條規則會咬到你。**先分清楚是哪一種再動筆。**

### A. 讀者不在場（冷讀）

程式碼註解、commit message、PR/MR 留言、設計文件、教學筆記、給非作者看的 review finding。他沒參與這次對話、沒讀過設計文件、可能連 diff 都沒看。**§2 §3 §4 全開。**

| 載體 | 讀者手上**有** | 讀者**沒有** |
| --- | --- | --- |
| **程式碼註解** | 這個檔案本身、同 repo 的 code（他 grep 得到、跳得過去） | 這次對話、設計文件、MR 討論串、git 歷史、被砍掉的舊 code、還沒 ship 的計畫 |
| **commit message** | 這次的 diff、當下的 repo | 這次對話、你考慮過又否決的做法、你腦裡的推理鏈 |
| **PR / MR 留言** | 這條 diff、repo、同一串前面公開的留言 | 私下討論、其他 MR 的內容（要引就給**絕對 URL**，相對路徑會壞） |
| **設計文件 / 教學筆記** | 只有這份文件本身 | 全部。標準最嚴，要讓**零知識的人**讀得懂 |

### B. 讀者在場，但沒有你腦裡的東西

session 回話。他跟著這串一路走過來，所以「剛剛那個做法」「上面那份文件」他接得住——**§2 的多數禁令對他不成立，硬套只是噪音。**

真正會漏的是**你知道、但從來沒說出口的那些**：

- 你 grep / Read 過但沒貼出來的檔案內容（最常見）
- subagent 回傳、你只吸收了結論卻沒轉述的東西
- 你在這一則回話裡臨時發明、卻沒定義的代稱

判準改成：**這句話依賴的東西，是「我們兩個都看到過」還是「只有我看到過」？** 只有我看到過就要當場攤開。

**§3（冒問號測試）和 §4（給機制不給類比）在這裡照樣全開**，而且 §4 本來就是對話情境的規則：對方說「我不懂 X」時要往具體機制鑽，不是換個生活化說法。

---

## 2. 規則一：只引用讀者手上有的東西

> **適用 §1-A（讀者不在場）的載體。** session 回話只需要遵守最後一條「只活在你腦裡的東西」。

### 一律禁止

- **指向 .md 文件 / 章節號**——「見 QA §C」「apple-sub.md §6.3」「詳見 design §12.1」。文件會 drift、跟 code 對不上就變成假資訊，還逼讀者跳檔。**一個都不准出現。**
- **自創的設計專有名詞**——「統一失敗模型」「貼法 A」「dedup gate」「中立接縫」。這些詞的意思只活在設計文件或某次對話裡，冷讀者從眼前的東西推不出來。
- **已被砍掉或改名的符號**——「從 `create()` 拆出這半」，冷讀者沒看過 `create()`。
- **重構當下的框架**——「原本…改成…」「拆出…這半」，只有正在改的人懂；改完就沒有「原本」了。
- **還沒落地的未來計畫**——「留待 recycle 落地」，讀者看不到那個計畫，只會以為自己漏讀了什麼。
- **只活在你腦裡的東西**（這條連 session 回話也要守）——你讀過但沒貼出來的檔案內容、subagent 回傳但你沒轉述的結果、你臨時發明卻沒定義的代稱。在冷讀載體還要多禁一層：「剛剛那個做法」「上面說的 plan B」這種**只有現在讀才懂的代稱**。

### 可以引用什麼

- **同 repo 看得到的 code 符號**：函式名、sibling method、檔案路徑。冷讀者開得起來。
- **外部事實，但要標明住處**：「Play Console 上的訂閱狀態」「Apple 的 server notification 送過來的欄位」。讓他知道去哪確認。

### 修法：就地把那條因果講完

不要丟一個自創詞或指標要人自己去查，把機制當場用白話講完。

```
❌ 依 apple-sub.md §6.3 的統一失敗模型，這裡沿用貼法 A。
✅ 這裡 throw 出去、交給外層標成失敗回 5xx，讓 Apple 平台重送這則通知；
   吞掉的話這筆事件就永遠遺失了。

❌ 從 create() 拆出這半，留待 recycle 落地。
✅ 頻道可以先建起來、viewer 資料每通通話現補，所以建頻道跟填 viewer 分兩支。

❌ ack 放在寫 outbox 之前（見 step.md）。
✅ ack 要放在寫 outbox 之前：寫 outbox 遇到重送會去重早退，
   放後面那條重送路徑就跑不到 ack、會漏 ack。
```

## 3. 規則二：逐句過「第一次讀到的人會不會冒問號」

寫完不是通篇看一遍，是**一句一句問**：他讀到這句會冒出什麼問號？會冒＝改。

### ① 講「為什麼不那樣做」時，先把問題問出來

讀者腦中的疑問要你先幫他問出口，再回答。替代方案要寫成**code 真的會長的樣子**，後果推到底。

```
❌ 不擋這種事件，因為權益仍算原主人。
✅ 那為什麼不乾脆在這裡丟 error 擋掉這種事件？因為 Apple 的 binding api 是以
   原始購買帳號為準：擋掉之後 findActiveByUserId 還是查得到原主人的訂閱，
   結果付錢的新帳號拿到零。
```

### ② 名詞要 grep 得到

用讀者能在 code / diff 裡搜到的具體名字，不要用你自己翻譯過的白話代稱。

```
❌ 一道歸屬查詢、上面改掛
✅ findActiveByUserId、relinkChain、binding api
```

### ③ 結論寫死，不要只寫機制讓他自己推

```
❌ 權益仍算原主人。
✅ 權益仍算原主人 —— 也就是付錢的新帳號拿到零。
```

### ④ 會誤導的安慰句不能擺前面、修正句不能擺句尾

略讀的人只拿走第一句。先講會踩到的那件事，再講緩解。

```
❌ 這條路徑基本上不會發生，除非使用者換 Apple ID 後重新訂閱。
✅ 使用者換 Apple ID 後重新訂閱就會走到這條路徑；其餘情況不會。
```

### ⑤ 討論串行話不進去；外部事實標明住處

reviewer 跟你之間的簡稱、當時吵過的稱呼，讀者沒參與過。要提外部世界的事實就說清楚在哪：「Play Console 上」「Apple 後台的 originalTransactionId」。

### ⑥ 段落開頭要回指

新段落不要突然冒出一個標題就開講，先接回上一段的哪句話。

```
❌ 已知缺口：
✅ 上面說「理應收不到」有一個例外：
```

## 4. 規則三：解釋給機制，不給生活類比，也不堆術語

有人說「我不懂 X」，要的是**把 X 本身攤得更開**，不是換個講法。

**方向記法：聽不懂時往更具體的機制與流程走，不是往更抽象或更生活化走。**

- 生活化譬喻（fd＝門票、核心物件＝場館）**禁止**——讀者很難從門票聯想回真實機制，只是多背一層對應關係。
- 反方向堆專有名詞（丟一串資料結構、併發原語的術語）**一樣沒用**——術語不是重點，「具體」才是。

### 攤開這四樣

1. **內容物**：這東西由哪些欄位／部件組成
2. **資料存在哪、怎麼流動**
3. **狀態行為**：滿了會怎樣、空了會怎樣、失敗會怎樣
4. **使用場景**：誰在什麼時候會碰到它

```
❌ fd 就像進場門票，核心的 file 物件是場館。
✅ fd 是一個 int，index 進 process 自己的 open file table。table 每一格指向一個
   file 物件，offset 跟 inode 記在 file 物件上、不在 fd 上。所以 dup 出來的兩個 fd
   指向同一個 file 物件、共用同一個 offset；分別 open 同一個檔案則是兩個 file 物件、
   offset 各走各的。
```

### 出現讀者可能不熟的名詞，就當場展開

不要假設自明。展開＝講它的內容物與行為，不是換個同義詞。

### 文件的標準更嚴：拆成可逐步跟隨的流程

讀者沒有任何上下文，所以照這個順序寫：

1. 這段設計要解決什麼問題
2. 展開涉及的名詞與它們的狀態
3. **正常情境走一遍**（每一步標出關鍵變數當下的值）
4. **失敗情境再走一遍**（同樣標值）
5. 最後才列缺陷與修法

寫完自問：沒跟過這段對話的人看得懂嗎？

### 分清文件類型

要「筆記／教學文件」時，**不要夾帶排查過程、log 節錄、事故統計**——那是排查紀錄，是另一種文件。教學文件只留可重複使用的機制與通則。

## 5. 各載體的示範

### commit message

寫給冷讀的 reviewer：先講**動機**（這次解決什麼問題、原本怎樣不好），再讓每個關鍵決策帶一條 why 的推理鏈。名詞只當脈絡裡的標籤，不是清單。

```
❌ 改用 notification V2 的 SUBSCRIBED type，加上 originalTransactionId 去重，
   接 UserSubscription enum。
   （純專有名詞清單，沒有邏輯跟思路）

✅ 訂閱狀態原本靠 client 回報，使用者沒開 app 就永遠不會更新，所以改成收
   Apple 的 server notification。同一筆訂閱 Apple 會重送多次，因此用
   originalTransactionId 當唯一鍵去重，重送的那幾筆在寫入前就早退。
```

### session 回話

對方有整串對話，缺的是**你讀過卻沒說出口的東西**。

```
❌ 我看了一下，這個 case repo 裡已經有處理了，照那邊的做法做就行。
   （「那邊」是我 grep 出來的，他沒開過那支檔——這是只有我看到過的東西）

✅ 我看了 subscriptionService.ts 的 createSubscription：它用 originalTransactionId
   當唯一鍵去重，重送的那幾筆在寫入 DB 前就早退。這個 case 照它做就行。
```

「剛剛那個方向」這種代稱在 session 裡是**合法的**——他跟著走過來，接得住。同一句話寫進 commit message 或註解才違規。

### 程式碼註解

只講「這段 code 本身為什麼這樣」，用檔案裡看得到的東西表達。

```
❌ // 這裡走統一失敗模型（詳見設計文件）
✅ // throw 交給外層標成失敗回 5xx，讓平台重送這則通知；吞掉這筆事件就永遠遺失
```

## 6. 收尾自檢清單

送出前逐條打勾。前四條**只在讀者不在場的載體**（註解 / commit / PR 留言 / 文件）檢查，其餘全載體都要過。

冷讀載體限定：

- [ ] 有沒有指向任何 .md 檔或章節號？（有＝刪掉，就地講完）
- [ ] 有沒有只活在設計文件／這次對話裡的自創詞？（有＝當場用白話展開那個機制）
- [ ] 有沒有提到被砍掉／改名的符號、重構過程、還沒落地的計畫？
- [ ] 有沒有「剛剛那個」「上面說的」這種只有現在讀才懂的代稱？

全載體（含 session 回話）：

- [ ] 有沒有哪句依賴「只有我看到過」的東西——我讀了沒貼的檔案、subagent 沒轉述的結果、我剛發明沒定義的詞？
- [ ] 每個名詞讀者 grep 得到嗎？
- [ ] 有沒有哪句只給機制、沒把結論寫死？
- [ ] 有沒有把安慰句擺前面、修正句擺句尾？
- [ ] 有沒有用生活化類比？有沒有反過來堆一串沒展開的術語？
- [ ] 段落開頭有沒有接回上一段？
- [ ] 最後一問：讀者手上真的有的東西，夠他讀懂這段嗎？
