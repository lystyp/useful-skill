替這份改動排一條由外往內的閱讀路線。

- 排路線前先當作 user 沒看過這份 code，白話具體說明原本遇到什麼問題、怎麼改的、為什麼要改、行為有沒有變。動機從附帶的說明（commit 訊息、描述、user 給的背景）抓。
- 先列出改動的入口。一個入口一條路線，照執行順序排站，不照檔名或 diff 順序。
- 每站給可點的 `檔案:行號`，加一句「這站看什麼」：只講這次改了什麼、它在流程裡負責哪一步。下層呼叫列在呼叫它的那站底下，讀完上層再跳下去。
- 第 0 站放資料形狀（schema／型別）的改動，後面每站都會讀寫它。
- 最後一站列對應的測試檔，說明「測試情境一覽」可以當規格表讀；附看 diff 的 git 指令，提醒新增的檔案 `git diff` 看不到。
- 行號用 grep 實際查，不憑記憶。
